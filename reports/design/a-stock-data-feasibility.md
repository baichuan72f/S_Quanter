# a-stock-data 接入可行性评估

> 状态：可行性评估（不改代码、不改数据、不动 `data/`；是否实施由人决定）
> 日期：2026-11-07
> 评估对象：`simonlin1212/a-stock-data`（V3.10.4，commit `f21534946c42`，Apache-2.0）
> 上游来源：GitHub issue #12；前序提案 `reports/design/a-stock-data-integration.md`（方案 B：并行双源）
> 前序评审 `reports/design/a-stock-data-review.md` 在仓库、远端分支与 PR 中均不存在，按评审要求忽略。
> 证据快照：工单环境实测 `queries.py` / `data/` / `bqcompat/`；上游按 commit `f215349` 的
> `SKILL.md`（7,702 行、442,341 字节、91 个 `python` 代码块）核对。所有数字均为 2026-11-07 实测。

**结论先行：作为“可参与跑批的新数据源”，可行性 5.4/10，低于 6，不建议在本期接入运行链路。**
可行的是把它降级为「只读、离线、独立目录的第二来源」，用重叠窗口对拍现有 DAI 快照；
即使按这个窄口径重评也只有约 6.2/10，仍不足以成为默认数据源。下文六节给出依据。

## 1. 收益

### 1.1 现有数据家底（实测）

`data/` 当前 10 张表、64 个 parquet 文件、95MB、合计 **5,281,222 行**：

| 表 | 行数 | 覆盖范围 | 分区 |
|---|---:|---|---|
| `trading_days` | 30,075 | 2010-01-04 ~ 2026-11-04，8 个市场 | 年 |
| `cn_stock_real_bar1d` | 117,094 | 2026-10-08 ~ 2026-11-05，5,578 只 | 月 |
| `cn_stock_bar1d` | 111,516 | 2026-10-08 ~ 2026-11-04 | 月 |
| `cn_fund_real_bar1d` | 45,302 | 2026-10-08 ~ 2026-11-05，2,164 只 | 年 |
| `cn_fund_bar1d` | 43,140 | 2026-10-08 ~ 2026-11-04 | 年 |
| `cn_stock_index_bar1d` | 79,844 | 2024-01-02 ~ 2026-11-05，121 个指数 | 年 |
| `cn_stock_instruments` | 1,428,829 | 2025-01-02 ~ 2026-11-04 快照 | 年 |
| `cn_stock_dividend` | 47,836 | 2010-01-15 ~ 2026-12-11 | 年 |
| `cn_fund_instruments` | 3,264,948 | 2010-01-04 ~ 2026-11-04 快照 | 年 |
| `cn_stock_prefactors` | 112,638 | 2026-10-08 ~ 2026-11-04，151 列 | 月 |

股票日线只有 **21 个行情日**（5,578 只/日）；而 `trading_days` 的 CN 日历到 11-04、区间内
只有 20 个交易日——**行情比日历多出 11-05 一天，两个 DAI 导出文件之间已经存在 1 天错位**。
这正是“单源无对拍”会积累的典型问题，也是第二来源最直接的收益点。

### 1.2 a-stock-data 能补什么（按能力逐项核对上游代码）

| 能力 | 上游实现与边界（commit `f215349`） | 对现有数据的补充 |
|---|---|---|
| 全市场股票日线 | `tdx_daily_package(date)`：通达信官网盘后包，约 2.7MB/日，个股 `volume` 单位股、`amount` 元；字段为 `date/market/code/name/prev_close/open/high/low/close/volume/amount`；非交易日/未发布 404 抛错；文档实测最早 **2021-08-16**，2021-01-04 已 404，且注明“未逐日验证” | 从 21 天扩到 **1,263 个 CN 交易日**（2021-08-16~2026-11-05），按 5,578 只/日估算约 **704 万行**，是现有 11.7 万行的 **约 60 倍**；补上 `amount`、`prev_close` |
| 指数日线 | `tencent_kline(code, period, adjust, start, end)`：单段最多 640 根、按 700 天分段翻页；**没有成交额**；指数清单要自己维护 | 现有 121 个指数只到 2024 年；可把抽样指数向前延长（以 640 根/段翻页） |
| 交易日历 | `trading_calendar(year, month)`：深交所整月日历，逐月请求；只能得到 A 股 | 现有已覆盖 2010 起 8 个市场，**无补充价值**，只能做 CN 日历的独立核对 |
| 分红 | `dividend_history(code)`：东财逐标的，字段仅 `date/bonus_rmb(每股)/transfer_ratio(每10股)/bonus_ratio(每10股)/plan`；无税后、登记日、公告日 | 现有 47,836 行、10 列、2010 起，字段更全；**无补充价值**，仅可抽样核对 |
| 复权因子 | `sina_adjust_factor(code, kind)` + `apply_adjust`：qfq 为除数、hfq 为乘数；基金走 s/u 折算口径 | 可重算复权价，但与 DAI 的累计 `adjust_factor` 是否等价**待对拍** |
| 估值/ST | `baostock_valuation_history`：2016 起 PE/PB/PS/PCF、换手率（百分数）、停牌、`isST`；**不支持北交所**，逐标的登录 | 可补部分 prefactors 字段，但无法复刻 151 列 |
| 额外能力 | 分钟线/逐笔、资金流、龙虎榜、两融、公告、期权、可转债等 | 属于新策略能力，需新表契约，不计入本次“接入现有数据源”的收益 |

### 1.3 口径一致性风险是否下降

**只下降了一部分，且不是关键部分。**

- 引擎行情契约（`engine/data_source.py:_BAR_COLUMNS`）共 10 列：
  `open/high/low/close/volume/pre_close/upper_limit/lower_limit/amount/adjust_factor`。
  TDX 盘后包可直接对上其中 7 列；`upper_limit/lower_limit/adjust_factor` 三列拿不到。
- 也就是说，能拿第二来源交叉验证的是**价格、成交量、成交额**；真正决定回测是否可信的
  **涨跌停价、复权因子、151 列 prefactors** 仍然是单源。
- 风险结构因此是“OHLCV 可对拍、衍生口径仍单点”。对 `dual_ma_demo` 这类只用
  `data.history` 的价格策略，收益最实在；对 `小市值` 系列几乎没有收益。

### 1.4 维护成本的变化

维护成本**上升**，不是下降：

- 新增一条 ETL 链路（下载、解析、映射、清单、校验、补缺口），目前仓库没有这类自动化；
- 现有链路是“BigQuant 导出 → 本地 parquet”，换/加源不减少 BigQuant 侧工作；
- 上游没有包、没有版本化数据快照，需自行 pin commit + 维护 manifest。

## 2. 风险

按“会炸程度”从高到低排序。影响面只列本仓库实际存在的策略/视图。

### R1. 涨跌停价、复权因子缺失 → 回测静默偏乐观（最高）

- **触发条件**：vendor 数据参与撮合（方案 A/C），而映射层把缺失列留空或填 0。
- **代码证据**：`engine/smalltrader.py:2355-2405` 中，`upper_limit/lower_limit` 缺失或 NaN 时
  取 `0.0`，随后 `is_buy and upper_v > 0 ...` 的一字板拦截条件不成立 → **涨停买得进、跌停卖得出**。
  `adjust_factor` 缺失时，基金分红只能靠事件表，`_prev_adjust_factor` 返回 `None`，
  基金份额折算会走 `cash_before_tax` 回退，ETF 轮动净值与平台口径出现系统性差异。
- **影响面**：`dual_ma_demo`、`轮动宝2本地`、`ETF轮动_年化45_大宽` 等所有经引擎撮合的股票/基金策略；
  以及 `sim_replay --verify` 的跨源对拍前提。
- **发现难度**：**极高**。不报错、不留日志，只能靠人工对拍净值或逐笔订单；
  按当前“无自动化测试”的现状，通常要等到净值明显偏离（数周~数月）才会发现。

### R2. 量纲错误 → 因子与流动性判断整体差 100 倍

- **触发条件**：映射层直接沿用上游字段单位。上游明确：TDX 个股 `volume` 是**股**；
  腾讯 K 线 `volume` 除科创板外是**手**；`baostock turn` 是**百分数**（0.31=0.31%），
  而本地 `turn` 是**小数**（0.006333=0.633%）；分红 `bonus_ratio/transfer_ratio` 是**每 10 股**，
  本地 `bonus_rate/conversed_rate` 是**每股**。
- **影响面**：成交量/换手率类因子、流动性过滤、成交额核对、分红送转；影响 `dual_ma_demo` 的
  成交量条件、所有用 `turn` 的因子、以及 `cn_stock_dividend` 对齐。
- **发现难度**：中。若做重叠窗口量纲核对，当天可发现；跳过核对则完全静默。

### R3. 停牌“缺行”与“volume=0”语义不一致 → 跑批被误判或回测少一天

- **触发条件**：TDX 盘后包对停牌标的可能没有记录，而本地 DAI 快照是“有行、`volume=0`”。
- **代码证据**：`paper/checks.py:check_data_ready` 把“持仓标的当日无行情行”判为数据残缺并中止；
  注释明确“停牌标的有行但 volume=0，属正常，不算缺行”。实测本地 21 天里有 **184 行**
  股票 `volume=0`（基金 666 行）。
- **影响面**：`run_daily.py` 每日跑批（会被中止，属“炸得响”）；回测侧则是缺一天，
  持仓无法按停牌价重估，净值曲线出现跳变。
- **发现难度**：跑批当天即知（好）；回测侧要等净值异常（差）。

### R4. `cn_stock_prefactors` 不可替代 → 小市值策略直接失效

- **触发条件**：把 vendor 数据根设为默认，或用方案 C 切换到 vendor。
- **证据**：本地 prefactors 为 151 列、112,638 行；`小市值5日轮动2` / `小市值sample`
  直接 SQL 读取 `st_status`、`is_risk_warning`、`total_market_cap`、`volume`、`close`。
  a-stock-data 没有等价大表（baostock 只覆盖部分估值/ST，且不支持北交所）。
- **影响面**：两个小市值策略；`bqcompat/dai_compat.py:_SUPPORTED` 里没有该表时会抛
  `DaiTableError`（这是正确行为），但若映射层造一张空表，会退化成“静默不下单”。
- **发现难度**：显式报错时立刻发现；空表/缺列时极难发现。

### R5. 数据不可复现 → 同一回测跑出不同结果

- **触发条件**：重跑 ETL、源站回填历史、上游修正解析。上游没有版本化数据快照，
  TDX 官网只保留有限历史（实测 2021-01-04 已 404），且“未逐日验证”。
- **影响面**：所有跨源回测、审计、`sim_replay --verify`；同一天两次更新可能得到不同 parquet。
- **发现难度**：高。只有做 manifest + 校验和并长期比对才会暴露；否则用户以为“本地数据=可复现”。

### R6. 上游与源站漂移 → ETL 断供或数据缺口

- **触发条件**：源站改版/限流/封 IP。实测上游仍活跃（11,566 star、2,098 fork、
  2026-08 以来 29 次提交、v3.10.0~v3.10.4 一个月内连发），但 open issue #63 正是
  “东财并发限流与 HTTPS 校验”；腾讯“单入口约 600 次后限流”，东财有封 IP 风控。
- **影响面**：ETL 更新失败或部分市场缺失；若吞掉异常写空表，会污染后续所有回测。
- **发现难度**：ETL 当时报错则低；静默降级则高（与 R5 叠加）。

### R7. 历史覆盖不完整 → 长窗口策略“以为有数据，其实起点更晚”

- **触发条件**：回补 2021-08 之前，或回补北交所 2022-05-06 之前（上游文档：此前包没有北交所文件）。
- **影响面**：`warmup_days` 420 天/120 天的策略；北交所标的池。
- **发现难度**：回补时报错可发现；中间缺口只能靠逐日 manifest 核对。

### R8. 依赖与数据许可

- **触发条件**：把上游复制进运行链路或分发。上游是抓取配方集合，不是可安装包；
  运行需 `requests/mootdx/baostock/stockstats` 等，与本仓库“运行依赖只有
  pandas/numpy/duckdb”冲突。代码 Apache-2.0，但行情/分红数据来自各网站，
  代码许可不覆盖数据再分发。
- **影响面**：离线分发包、`requirements.txt`、合规。
- **发现难度**：打包/分发时暴露；法律风险滞后。

### R9. 混源审计（仅在方案 C 下）

- **触发条件**：同一 `strategy_id` 先后用 `bigquant` 与 `astock` 跑批。
- **影响面**：`state/paper.db` 净值曲线混源，绩效不可比；看板无来源标签。
- **发现难度**：高，需要看库或人工记忆。

## 3. 成本

### 3.1 改造量

| 方案 | 涉及文件 | 行数量级 | 说明 |
|---|---|---:|---|
| 只读对拍（提案方案 B 的窄版） | 新增 `datadownload/astock/` 约 5 个文件：抓取、映射、manifest、compare、README | 新增 **650~900 行** | 运行侧 **0 行**：`queries.connect(root=...)` 与 `LocalParquetDataSource(data_dir=...)` 已存在；甚至可用 `LOCALBQ_DATA_DIR` 环境变量把整条链路指向 vendor 根做对拍 |
| 按策略切换（提案方案 C） | `paper/runner.py`、`run_daily.py`、`sim_replay.py`、`engine/data_source.py`、`paper/local_data.py`、`dashboard.py`、`paper/webdata.py`、`strategies/*.meta.json`、状态库 | 改动 **8~9 个文件、250~450 行**，另加状态库字段迁移与 UI | 还需处理缺表显式失败、来源标签、混源审计 |
| 直接替换（提案方案 A） | 上述全部 + 策略 SQL 重写 | **千行级**，且失败面覆盖数据、策略、分发 | 不建议 |

现有可复用面（降低改造成本的事实）：

- `queries.py` 的 `TABLES` 是纯目录/glob 声明，`connect(root=...)` 已支持任意数据根；
- `engine/data_source.LocalDuckDataSource(data_root=...)`、`paper/local_data.LocalParquetDataSource(data_dir=...)`
  都已支持切换数据根；
- `bqcompat` 只做 SQL 方言翻译，不绑定数据来源；只要表名/列名一致即可复用。

### 3.2 日常运维成本

- **每日更新**：TDX 盘后包约 2.7MB/日；下载 + 解析 + 落 parquet + 清单，预计 1~3 分钟/日
  （未计网络重试）。一年约 250 个交易日、约 675MB 下载量。
- **一次性回补**：2021-08-16 起 1,263 个交易日、约 3.4GB 下载；串行请求按 1~2 秒/日估算
  约 **20~45 分钟**（含解析）。
- **磁盘**：按当前 117,094 行/7.67MB 的比例（约 65.5 字节/行）估算，704 万行约 **460MB**；
  日增量约 0.4MB。相对现有 95MB 是 4~5 倍。
- **依赖升级**：上游无包、无 semver API，只能 pin commit + vendor 副本；每月/每季检查
  CHANGELOG 与源站变化，升级需重跑全量对拍。
- **校验成本**：每次更新需记录 manifest（URL、下载时间、行数、校验和）并跑覆盖/量纲检查；
  否则 R5/R6 无法定位。

### 3.3 外部依赖风险评估

|---|---|---|

## 4. 可行性评分

评分对象是「把 a-stock-data 接入为可参与跑批的数据源（含并行双源）」。权重按本项目最在意的
“能否补上数据”优先，其次依赖稳定、方言兼容、可回滚。

| 维度 | 权重 | 得分 | 打分依据 |
|---|---:|---:|---|
| 数据可得性 | 40% | **4.0** | 股票日线可从 2021-08 起补到约 704 万行（60 倍），但缺 `adjust_factor/upper_limit/lower_limit` 三根引擎关键列；prefactors 151 列不可复刻；基金全量清单、历史名称快照、税后分红/登记日均缺；指数/日历/分红无增量价值 |
| 依赖稳定性 | 25% | **5.0** | 上游很活跃（11.5k star、月内 4 个版本），但无包、无 API 版本、无数据快照、无 SLA；源站限流/改版直接传导；测试依赖真实网络 |
| 与 `bqcompat/` 方言层兼容性 | 20% | **6.5** | 方言层只翻译 SQL 函数（44 个已注册、8 个明确不支持），与数据来源解耦；同 schema 即可用；缺表会抛 `DaiTableError`（显式失败，正确）。扣分在缺列/量纲语义与 prefactors 不可用，不是方言层本身 |
| 可回滚性 | 15% | **8.5** | 只读方案放独立目录，删目录即回滚，`data/` 不变；运行侧零改动。若上方案 C，状态库混源回滚需要人工处理，故不给满分 |
| **加权合计** | 100% | **5.4** | 4.0×0.40 + 5.0×0.25 + 6.5×0.20 + 8.5×0.15 = **5.425** |

**分档说明**：按“能补数据但关键口径仍单源、依赖不可复现”判断为 5.4，属“可做只读校验，
不宜进运行链路”。若把范围收窄为「只读、不入跑批、只做重叠窗口对拍」，数据可得性可给 5.5、
依赖 5.0、兼容 7.0、回滚 9.0，加权约 **6.2**——仍低于“可作为默认/并行跑批数据源”的门槛
（那需要 ≥7）。

## 5. 若可行性 < 6：替代方案

本期主评分 5.4 < 6，给出三个替代方案。**以下都只是候选，标注“待再次评审”，不替人拍板。**

### 替代 A：维持单源，先把「导出 → 清单 → 校验」闭环补齐

- **做法**：不改数据源；给现有 `datadownload/export_*.py` 增加 manifest（日期、行数、校验和）、
  给每日跑批增加“行情日期 vs 日历日期一致”“各表最新日期一致”检查（当前已实测出差 1 天）。
- **适用条件**：只需要更长的 DAI 历史，且仍有 BigQuant 账号；不想引入第二套抓取。
- **代价**：约 1~2 个脚本、100~200 行；仍依赖 BigQuant 账号与平台侧导出；没有第二来源，
  无法独立验证 DAI 是否正确。
- **收益**：直接消掉“行情比日历多一天”这类问题；成本最低、风险最小。

### 替代 B：只引入 baostock 做抽样对拍（不落库、不参与跑批）

- **做法**：ETL 侧按需抽样 20~50 只股票，用 `baostock_valuation_history` / 其日线接口
  对拍 DAI 的 OHLCV、停牌、ST；结果写 Markdown 报告，不生成 parquet、不改 `data/`。
- **适用条件**：目标只是回答“DAI 是否可信”，能接受抽样而非全市场；不需要历史回补。
- **代价**：`baostock` 一个 ETL 侧依赖（SDK 有版本、比抓网页稳定）；逐标的登录，样本量大时慢；
  不支持北交所；只能验证有交集的字段。
- **收益**：以最小改造拿到独立校验证据；失败可完全丢弃，不影响运行链路。

### 替代 C：只把 TDX 盘后包做成独立只读历史行情集（研究/对拍用）

- **做法**：按提案方案 B 的窄版，只落 `cn_stock_real_bar1d`（2021-08 起）与抽样指数，
  放独立根目录，用 `LOCALBQ_DATA_DIR`/`data_dir` 指向它做研究和对拍；**不接 `run_daily`，
  不设为默认，不提供策略切换开关**。涨跌停价/复权因子先留空并在文档标注。
- **适用条件**：确实需要 5 年全市场日线做研究/因子验证，且能接受“只读、不可撮合”。
- **代价**：5 个 ETL 文件、650~900 行；磁盘约 460MB；一次性回补 20~45 分钟；
  需要 manifest 与量纲校验，否则 R2/R5 会静默发生。
- **收益**：把 21 天扩到 1,263 天（约 60 倍），且不触碰现有跑批与 `data/`。

**三者可组合**：先做替代 A（低成本治理现状），需要独立证据时做替代 B（抽样），
确有长历史研究需求再做替代 C（只读数据集）。任何一步要升级为“参与跑批”，都必须重新评审，
并先补上 §2 的 R1/R3/R4 口径。
