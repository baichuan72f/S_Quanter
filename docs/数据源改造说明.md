## 0. 结论先行

1. **数据层是分层的，改数据源通常不需要动撮合引擎。** 链路是
   `parquet 快照 → queries.py（DuckDB 视图）→ engine/data_source.py（数据源）
   → paper/local_data.py（模拟盘适配层）→ runner / dashboard / sim_replay`。
   只要保持第 3 节的表契约和接口契约，`engine/smalltrader.py` 可以完全不动。
2. **当前本地数据只覆盖最近约一个月（股票/基金）**。长回看窗口的策略不会报错，
   而是因子算不出、**静默不下单**。改造前先确认是“补历史数据”还是“换数据源”，
   两者的工作量和风险不同。
3. **把数据层拆到另一个 GitHub 仓储是可行的，但边界要选对**：建议新仓只放
   “数据目录 + DuckDB 查询 + 数据源实现 + 导出脚本 + schema/测试”，
   `smalltrader`、状态库、看板、`bqcompat` 留在主仓；主仓保留 `queries.py`
   薄壳，避免几十个策略 notebook 的 `import queries` 全部失效。
4. **新仓不能破坏“拷贝目录即可离线运行”的分发方式**。主仓目前是可整目录拷到
   Windows 机器直接跑的分发包；引入外部包依赖前，必须在“pip 安装”与
   “vendor 同步副本”之间做明确选择（见第 9 节）。
5. **GitHub 能力（实测）**：当前账号 `changchuanheliu` 能在自己名下新建仓库；
   **不能**在 `baichuan72f` 名下新建（那是个人账号，不是组织）；也**不能删除**
   仓库（token 没有 `delete_repo`）。而且本部署只监听 `baichuan72f/SmallQuant`，
   新仓的 PR 不会被工单系统自动绑定。详见第 10 节。

## 1. 当前数据链路

```text
BigQuant DAI（云端）
  └─ datadownload/export_*.py        在 BigQuant 侧执行（bigquant + polars）
       └─ data/<表名>/<YYYYMM|YYYY>.parquet
            │  不入 Git；根目录可用 LOCALBQ_DATA_DIR 覆盖
            ▼
        queries.py                   DuckDB 内存库：按 TABLES 建 v_<表> 与裸名视图
            ├─ engine/data_source.py  LocalDuckDataSource（StockDataSource 子类）
            │     └─ _auto_fetch_backtest_data → smalltrader.run(data=缺省) 自动取数
            ├─ paper/local_data.py    LocalParquetDataSource（代码风格/日历/标的池适配）
            │     └─ paper/runner.py → paper/checks.py（数据校验）→ smalltrader
            │     └─ paper/webdata.py / dashboard.py（证券名称兜底）
            ├─ bqcompat/dai_compat.py 把策略里的 dai.query / DataSource 接到本地视图
            └─ sim_replay.py          历史回放与一次性回测对拍
```

各层职责与改动优先级：

| 文件 | 职责 | 改造时是否常动 |
|---|---|---|
| `data/` | parquet 快照，按表分目录，按月/按年分文件 | 数据改造的主战场 |
| `queries.py` | 表清单 `TABLES`、视图注册、数据根目录解析 | 新增/改表时必动 |
| `engine/data_source.py` | 行情/分红/名称/基准取数，回测自动取数注册 | 换存储或换表结构时动 |
| `paper/local_data.py` | 平台代码风格 ↔ 本地代码、交易日历、标的池、跑批辅助 | 表名/代码风格变化时动 |
| `paper/checks.py` | 跑批前数据完整性校验（行数、缺行、NaN） | 表名或校验口径变化时动 |
| `bqcompat/dai_compat.py` | 策略 SQL 的 `dai` 兼容层 | 新增平台表时动 |
| `engine/smalltrader.py` | 撮合引擎，只消费 `dict[symbol, DataFrame]` | 一般不动 |
| `paper/runner.py`、`dashboard.py`、`sim_replay.py` | 状态、展示、回放 | 一般不动，但硬编码表名处要跟着改 |

## 3. 必须保持的契约

### 3.1 表与视图契约

- 表名与 BigQuant 平台一致，策略里的 SQL 才能不改。
- 每张表同时提供 `v_<表名>` 和裸名 `<表名>` 两个视图（`queries.connect()`）。
- 视图只读 `data/<表名>/` 下的 parquet；`TABLES` 中的 `glob`、`where` 决定读哪些文件/行。
- 没有 parquet 的表**不建视图**；查询会抛 `Catalog Error`，`dai_compat` 会转成
  可读的 `DaiTableError`（列出本地可用表）。不要用“静默返回空表”替代报错。
- 分区粒度不进入接口：按月、按年都行，`queries` 会把目录下所有非空 parquet 一起读；
  但分区决定增量更新和查询裁剪的效率。
- 空文件（0 字节）会被跳过；导出脚本留下的 0 字节占位不会让 DuckDB 报错。

### 3.2 数据源接口契约

`engine/data_source.py` 的抽象基类 `StockDataSource` 是换数据源的最低要求：

```python
class StockDataSource(ABC):
    def get_bar_data(instruments, start_date, end_date) -> dict[str, DataFrame]
    def get_dividend_events(instruments, start_date, end_date) -> DataFrame
```

`LocalDuckDataSource` 在此基础上还提供：

- `get_fund_dividend_events(...)`：本地没有基金分红表，用 `adjust_factor` 跳变反推
  份额折算事件（`is_fund_split=1`）。
- `get_instrument_names(...)`、`get_t0_instruments(...)`（本地恒为空集）、
  `get_index_bar_data(...)`。
- `get_fund_backtest_data(...)` / `get_stock_backtest_data(...)`：一站式组装
  `smalltrader.run()` 所需关键字参数。
- 模块导入时把 `_auto_fetch_backtest_data` 注册为引擎的 `_AUTO_LOADER`，因此
  `import data_source` 后 `bigtrader.run(data=...)` 缺省即可自动取数。

### 3.3 模拟盘适配层契约（`paper/local_data.py`）

| 方法 | 被谁用 | 契约 |
|---|---|---|
| `expand_pool(instruments, lookback_days=30)` | runner | 展开 `全市场股票/全市场基金` 预设，只取近 N 日有行情的标的 |
| `get_bar_data(...)` | runner / sim_replay | 返回键还原成调用方代码风格；DataFrame 以日期为索引 |
| `get_index_bar_data(...)` | runner | 基准缺失返回空表，由调用方中止（不要抛到页面） |
| `get_dividend_events(...)` | runner / sim_replay | 出参列名 `ex_date`（引擎按它分组）；含基金 `is_fund_split` |
| `get_instrument_names(...)` | runner / dashboard | 名称缺失不阻塞，退化为显示代码 |
| `get_trading_days(start, end, market_code='CN')` | runner / checks | 闭区间、升序、`YYYY-MM-DD` 字符串 |
| `next_trading_day(after)` | runner / notify | **严格大于** `after`；日历未覆盖返回 `None` |
| `latest_bar_date(instruments, benchmark)` | run_daily / dashboard | 取池与基准最新日的较小值，用于判断“数据是否到位” |
| `_read_parts(table, start, end, ...)` | checks | 按本地代码风格过滤，日粒度计数用 |

`paper/checks.py` 另有硬编码的表名和基金代码前缀，换表名/代码规则时必须同步。

### 3.4 策略侧契约

策略可以用三种方式取数：

1. `import queries; queries.connect().execute(...)`；
2. `import dai; dai.query(sql)`（`bqcompat` 把 `dai` 指到本地 DuckDB）；
3. `bigtrader.run(...)` 缺省 `data`，由 `engine/data_source.py` 自动取数。

因此 `queries` 这个模块名、`connect()`、`TABLES`、`DATA_ROOT` 都是对外契约。
替换实现时最安全的是**保留同名模块做薄壳**，而不是让所有策略改 import。

## 4. 改造场景与改动面

| 想做的事 | 要不要改代码 | 必改位置 | 主要风险 |
|---|---|---|---|
| 只补更多月份/年份的历史行情 | 否 | 只补 `data/<表>/` 下同 schema 文件 | 预热不够会静默不下单；内存/查询变慢 |
| 同一张表新增列（策略 SQL 用） | 否 | 无需改，`SELECT *` 视图自动可见；但所有分区文件必须同 schema（见 7.13） | 字段单位/口径要与云端一致 |
| 新增一张平台表 | 是 | `queries.TABLES`；`bqcompat/dai_compat._SUPPORTED`（只影响缺表提示，不影响 SQL 执行） | 忘记注册会导致“本地没有这张表” |
| 引擎/模拟盘需要新列 | 是 | `engine/data_source._BAR_COLUMNS`、`paper/local_data` 注释/列清单、`checks` 核心列 | 列缺失时引擎可能静默跳过 |
| 换行情表名/结构调整 | 是 | `LocalDuckDataSource` 默认参数、`local_data`、`checks`、`sim_replay` 硬编码表名 | 一处漏改导致部分路径读旧表 |
| 换数据供应商（schema 不同） | 是 | 新增 ETL/映射层，落成**现有 canonical schema** | 口径漂移（复权、涨跌停、停牌、成交量单位） |
| 换存储/查询层（不再 DuckDB） | 是 | 新写 `StockDataSource` 子类 + 适配层；重写 `_read_parts`/`expand_pool`/`latest_bar_date`/日历查询 | 接口面比想象大；性能与 Windows 部署 |
| 基金分红改用真实分红表 | 是 | `queries.TABLES` 加 `cn_fund_dividend`、`get_fund_dividend_events` 改读表 | 与 `adjust_factor` 口径对账 |
| 增加 T+0 标志 | 是 | `get_t0_instruments` + `local_data` 暴露 + 引擎传参 | 跨境/商品 ETF 的 T+1 假设会变 |
| 换交易日历来源 | 是 | `local_data` 的 `get_trading_days` / `next_trading_day` | T+1 委托清单与漏跑判断 |

**判断标准**：如果改动只是“同一张表、同一 schema、更多数据”，可以零代码；
只要表名、列名、代码风格、日期口径、分区位置任一变化，就必须按第 5 节逐层验证。

## 5. 标准改造步骤

### 第 0 步：记录基线

```bat
.venv\Scripts\python.exe queries.py
.venv\Scripts\python.exe run_daily.py --strategy strategies\小市值5日轮动2.ipynb --status
```

把表清单、行数、日期范围记下来（可直接用本文第 2 节的表）。改造后逐项对比，
避免“看起来能跑、数字其实变了”。

### 第 1 步：先定表契约

在动代码前写清楚：

- 表名（必须与平台一致，除非同时改 `bqcompat`）；
- 分区粒度（月/年）与文件名格式（`YYYYMM.parquet` / `YYYY.parquet`）；
- 列名、类型、单位、时区/日期口径；
- 主键/唯一性（通常是 `date + instrument`）；
- 缺失值语义（停牌是“有行、volume=0”还是“无行”）；
- 更新频率与最晚到位时间。

建议把这份契约写进新仓的 `docs/schema.md`，并在 CI 里用样例 parquet 校验。

### 第 2 步：落数据

- 放到 `data/<表名>/` 下；根目录不同时设 `LOCALBQ_DATA_DIR`。
- 用 zstd 压缩；不要提交到 Git（`.gitignore` 已排除 `data/`、`*.parquet`）。
- 断点续传脚本会跳过已存在且非空的文件；补历史时注意**不要覆盖**已有月份。
- 读取端会跳过 0 字节文件，`table_exists` 也按“非空文件数 > 0”判断；因此
  只有空占位文件的表**不会**建视图。空月份可以不落文件，或落占位文件但要
  知道它不会让表“存在”。

### 第 3 步：注册视图

新表在 `queries.py` 的 `TABLES` 中增加一条：

```python
dict(name="cn_fund_dividend", glob="cn_fund_dividend/*.parquet",
     desc="基金分红事件表(按年)"),
```

如有无效行，用 `where=` 过滤（参考 `cn_stock_prefactors` 的
`date IS NOT NULL`）。改完跑 `queries.py` 确认新视图 `[✔]`。

### 第 4 步：实现/调整数据源

- 只换数据来源、不改接口：继承 `StockDataSource`，实现两个抽象方法；
- 继续用 DuckDB：优先复用 `LocalDuckDataSource`，通过构造参数换表名；
- 保留 `_engine_module()` 的惰性导入方式，避免包式/扁平式两种布局下循环导入；
- 大数据量时沿用 `_chunks()`（每批 600 个代码）避免 SQL 过长；
- 返回的 DataFrame 必须：日期索引升序、数值列为数值型、键为调用方代码风格。

### 第 5 步：接适配层

- 代码风格映射：`_SUFFIX_TO_LOCAL` 目前只认 `SZA/SHE/SHA/SSE`，新供应商后缀不同要补；
- 交易日历：`trading_days` 表不存在或未覆盖时，`next_trading_day` 返回 `None`，
  跑批会提示“委托清单未生成”，不要让它静默变成“今天不交易”；
- 标的池预设：`POOL_PRESETS` 与 `expand_pool` 的表名要同步；
- `latest_bar_date` 同时看池和基准，基准滞后时按基准对齐。

### 第 6 步：策略兼容层

- `bqcompat/dai_compat._SUPPORTED` 增删表名；
- 新表若有平台扩展函数（`m_*`/`c_*`），确认 `bqcompat/daisql` 能翻译；
- 策略里如果直接用 `queries.connect()`，确认视图名与列名没变。

### 第 7 步：校验与回归

见第 6 节。没有自动化测试，**必须把命令输出贴进 PR**。

### 第 8 步：同步文档

- 更新本文件第 2 节快照；
- 更新 `README.md` 的“数据”表（当前已有多处过期）；
- 更新 `AGENTS.md` 的仓库边界/依赖说明（如有变化）。

## 7. 已知坑与约束（实测）

1. **新增分区文件对“新进程”生效，对常驻进程不生效。**
   `queries.connect()` 在建视图时把当时的文件列表写死进 `read_parquet([...])`；
   `LocalDuckDataSource` 又按 `data_root` 缓存连接。`run_daily` 每天新起进程没问题，
   但看板/长驻服务需要重启才能看到新月份。README 的“新增文件即生效，不用重建视图”
   只在“重新建连接”的意义上成立。
2. **因子表拆目录不一致。** `export_prefactors.py` 把 2020 年及以后写到
   `data/cn_stock_prefactors_2020p/`，但 `queries.TABLES` 只 glob
   `cn_stock_prefactors/*.parquet`。当前快照只有 2026 年 10/11 月，暂时没暴露；
   一旦补 2020 年以后历史，2020+ 会**不可见**。改造时必须对齐（改 glob 或改导出目录）。
3. **导出脚本是平台侧脚本，不是本地脚本。** `datadownload/export_*.py` 需要
   `bigquant`、`polars`、`log_util`（本仓库没有 `log_util`），
   `export_prefactors.py` 还写死了 `/home/aiuser/work/...csv` 字段文件路径。
   本地只保证 pandas/numpy/duckdb 三个依赖；不要把导出依赖加进 `requirements.txt`。
4. **只有约一个月行情。** `warmup_days` 大于数据覆盖范围的策略不会报错，
   而是不产生成交（见 README 对照表）。数据改造后要重跑这些策略确认信号恢复。
5. **日历比行情少一天（2026-11-08 复核）。** `trading_days` 的 8 个市场都只到
   2026-11-04，而 `cn_stock_real_bar1d` / `cn_fund_real_bar1d` /
   `cn_stock_index_bar1d` 到 2026-11-05；`data/trading_days/2026.parquet` 里
   2026-11-05 一行都没有。用 11-05 跑批会提示“交易日历未覆盖 T+1，委托清单未生成”。
   **根因在数据侧（导出时云端日历尚未包含 11-05），不是仓库代码截断：**
   - `queries.py` 的 `trading_days` 视图（第 52 行）没有 `where` 条件，
     `read_sql()`（第 94–102 行）只把目录下所有非空 parquet 拼成
     `read_parquet([...])`，不会排除最后一天；
   - `datadownload/export_p0.py` 的窗口是自然月首末日（第 38–42 行），
     `filters` 为闭区间（第 66 行），不会提前一天截断；
   - 现有 `data/trading_days/` 是**年分区**（2010–2026），而仓库内
     `export_p0.py` 只写月分区，说明当前年文件不是该脚本产出的，仓库里也没有
     年分区日历的重导脚本。

   **处理办法：在能访问 BigQuant DAI 的机器上重导当年日历。** 本机没有
   `bigquant` 包和 `~/.bigquant` 凭据，无法本地生成，也不要用行情表反推日历
   补行（会掩盖下一次源数据滞后）。在仓库根目录执行：

   ```bash
   python - <<'PY'
   from pathlib import Path
   from bigquant import dai, init_from_config
   import polars as pl

   init_from_config()            # 需先 bq auth login 或 bq auth --apikey 'AK.SK'
   year = 2026                   # 按需改成要补的年份
   out = Path("data/trading_days") / f"{year}.parquet"
   out.parent.mkdir(parents=True, exist_ok=True)
   df = dai.query(
       "SELECT * FROM trading_days",
       filters={"date": [f"{year}-01-01", f"{year}-12-31"]},
   ).df()
   if df.empty:
       raise SystemExit(f"[!!] {year} 日历为空，未写入 {out}")
   tmp = out.with_suffix(".parquet.tmp")
   pl.from_pandas(df).write_parquet(tmp)
   tmp.replace(out)
   print(f"[ok] {out} rows={len(df)} max_date={df['date'].max()}")
   PY
   ```

   把生成的 `data/trading_days/2026.parquet` 拷回本地后，按第 6.2 节
   “日历与行情是否对齐”的两条 SQL 验收（期望日历最新日期 ≥ 行情最新日期），
   再跑 `queries.py` 和 `run_daily.py --strategy ... --status`；常驻看板需重启
   才能看到新文件。这一步需要**持有 BigQuant 账号凭据的人**执行，本地环境与
   CI 都做不到。
6. **基金分类有两份实现。** `engine/data_source.split_fund_stock` 与
   `paper/checks.py` 里的前缀列表各写了一份；新增基金代码段时要同时改。
7. **`paper/local_data._BAR_COLUMNS` 实际未被使用**，只是文档性常量；
   真正裁剪列的是 `engine/data_source._BAR_COLUMNS`。改列时别只改一处。
8. **`paper/local_data.py` 顶部注释说数据默认在“项目上一级”**，实际
   `queries.DATA_ROOT` 优先项目内 `data/`。以代码为准。
9. **README 的数据范围已过期**：指数写 2010–2026，实际 2024–2026。改造时顺手
   修正，避免误导后续排障；`.venv` 的具体体积/包清单以目标 Windows 机器为准，
   工单环境的 `.venv` 与内置分发包不是同一份。
10. **代码风格转换只覆盖四种后缀**；新供应商若用 `.XSHE` 等，需扩展映射，
    否则本地代码匹配不上，表现为“标的池为空”或“无行情”。
11. **日期过滤是字符串拼接 SQL**，只用于内部可信参数；若未来接入外部输入，
    应改成参数化查询。
12. **删除/重建 `data/` 前先确认 junction/链接关系**；工单目录里它是链接，
    删错会影响所有工单和主 checkout。
13. **同一张表的分区文件必须 schema 一致。** `read_parquet([...])` 默认按第一个
    文件定 schema；只给新月份加列会导致 `Schema mismatch`。要么所有分区一起重导，
    要么给 `read_sql` 加 `union_by_name=true`（会带来缺列 NULL，需评估下游）。

| P1 | **导出幂等/可回填**：按表/区间补数，失败重试，记录导出日志 | 迁移现有 `export_*.py` |
| P1 | **原始数据校验**：导出后立刻做行数/日期/主键校验，坏数据不进 `data/` | 导出脚本后置钩子 |
| P2 | **多数据源适配**：canonical schema + vendor 映射层 | 新仓 `sources/` |

## 9. 拆到独立 GitHub 仓储的建议

### 9.1 推荐边界

**搬到新仓（数据层）：**

```text
smallquant-data/                  # 仓库名待定
├─ sqdata/
│  ├─ __init__.py                 # connect / TABLES / DATA_ROOT / 数据源类
│  ├─ catalog.py                  # 表清单与 parquet 发现（现 queries.TABLES）
│  ├─ duck.py                     # DuckDB 连接与视图注册（现 queries.connect）
│  ├─ sources.py                  # StockDataSource / LocalDuckDataSource
│  └─ paper_adapter.py            # LocalParquetDataSource（代码风格/日历/池）
├─ tools/export_*.py              # 现 datadownload/
├─ docs/schema.md
├─ tests/
└─ pyproject.toml                 # 依赖仅 pandas / numpy / duckdb
```

**留在主仓（消费方）：**

- `engine/smalltrader.py`（撮合引擎，数据契约的消费方）；
- `paper/runner.py`、`paper/store.py`、`paper/checks.py`、`dashboard.py`；
- `bqcompat/`（平台包名/SQL 兼容，属于“策略运行环境”，不是数据本身）；
- `queries.py` 保留为**薄壳**：`from sqdata.duck import *`、`TABLES = ...`，
  这样策略 notebook 里的 `import queries` 一行都不用改。

`engine/data_source.py` 的自动取数注册建议改成显式调用：新仓提供
`register_auto_loader(smalltrader_module)`，主仓在启动时调用；
避免新仓反向 import 主仓引擎造成循环依赖。

### 9.2 主仓如何依赖新仓（三选一）

| 方式 | 优点 | 缺点 | 适用 |
|---|---|---|---|
| `pip install -e ../smallquant-data`（或 git+https；内置 venv 需先 `ensurepip`） | 标准、版本清晰 | 分发 zip 不再自包含；需 pip/网络 | 开发机 |
| git submodule + `sys.path` | 两仓独立、可锁 commit | Windows 用户不会用；分发 zip 失效 | 内部开发 |
| vendor 同步副本（脚本把 `sqdata/` 拷进主仓） | 保持“整目录拷贝即可离线运行” | 两份代码需 CI 校验一致 | 需要继续离线分发 |

**建议**：如果 SmallQuant 仍要作为“拷目录就能跑”的分发包，选 **vendor 同步**：
新仓是开发主仓，发布时用脚本同步 `sqdata/` 到 SmallQuant，并在 CI 里比对哈希。
如果只在开发机跑，选 editable install 最省事。**不要**为了拆仓破坏离线分发。

### 9.3 迁移顺序（低风险）

1. 在主仓内先把 `queries.py` / `data_source.py` / `local_data.py` 的公共 API
   收敛成 `sqdata` 的接口（不移动文件，只加门面）；
2. 用同一份 `data/` 跑基线：`queries.py`、`run_daily --status`、
   `sim_replay --verify`，记录数值；
3. 新建空仓，迁入 `sqdata/` + 导出脚本 + schema/测试，CI 跑通；
4. 主仓改为依赖新包（按 9.2 选型），保留 `queries.py` 薄壳；
5. 双跑对比同一区间净值，确认无差异后删旧实现；
6. 更新 README/AGENTS/本文件。

### 9.4 风险

- **两仓 PR 协调**：一次数据改造可能同时要改新仓和主仓；本工单系统一个工单只绑定
  一个 PR，拆仓后需要拆成多个工单或人工协调。
- **接口漂移**：`queries` 既是模块名又是策略契约，薄壳必须长期保留。
- **数据不进 Git**：95MB parquet 且持续增长，新仓只放代码；共享数据用对象存储/
  发布包，不要默认上 Git LFS。
- **Windows 优先**：路径、编码、`.bat`、`pyarrow`/polars 的 Windows wheel 都要在
  Windows 上验证；Linux CI 只能覆盖逻辑，不覆盖分发。
